# Web applications

The public site applications and the shared packages they build on. Studio is a
separate subsystem with a different authorization boundary. Local detail lives in
[web/README.md](../../../web/README.md).

## Responsibility

Serve the three public sites - `jublawoma.ch`, `uncle-t.ch` and
`zelglihof-maegenwil.ch` - as independent TanStack Start applications. Each site
owns its routes, content tables, forms, visual language, build and release. No
site imports another site's implementation or tables.

## Inside

```text
web/
  sites/
    jublawoma/  unclet/  zelglihof/   one deployable per site
    studio/                            separate subsystem
  packages/
    contracts/                 shared validation, site ids, links, page contracts
    ui/                        shared behavior only where two sites need it
    i18n/                      Paraglide catalog and generated runtime
    query/  http-client/       client data fetching and typed HTTP
    identity/ assets/ messaging/  typed clients for the Java services
    queue/                     insert one prepared message in the caller's transaction
    database/                  Drizzle connections, transaction types, column helpers
    *-data/                    site domain packages (jublawoma, unclet, zelglihof)
    environment/               Vite environment loading
```

A site's source tree:

```text
src/
  components/   visual components named for what they render
  data/         feature reads, mutations and server functions
  model/        public view models and presentation helpers
  routes/       TanStack route definitions and page composition
  server/       runtime infrastructure such as database setup
  fonts.css  styles.css
```

Data packages use `<feature>.<role>.ts`, for example `donation.repository.ts`,
`donation.service.ts` and `public.repository.ts`. Repositories are SQL-visible;
services own rules, transactions and queue inserts; each site adapts records to
its own view models.

## Flow: a durable public form

This is the most failure-sensitive path in the web layer.

1. The browser renders one shared Zod schema and generates one submission id per
   form fill (a hidden field).
2. The site server function re-validates and calls the site's domain service.
3. The service opens a transaction:
   - checks the submission id against a unique index; a replay returns the
     original outcome,
   - locks the affected stock or donation-capacity row,
   - writes the durable row with its snapshot and status,
   - inserts the notification into `queue.message` in the same transaction.
4. The response carries a stable reference derived from the submission id.
5. A retry after a timeout or refresh cannot duplicate the row, decrement stock
   twice or send a second email.

Terminal and moderation states are per workflow; shared spelling is not shared
meaning. See [database/README.md](../../../database/README.md) for the status
vocabulary and constraints.

## Rendering and content

- Server-side rendering on Node via Nitro. Cache headers belong to the app, not
  the proxy.
- Public images are proxied through the site origin (`/api/assets/<id>?size=...`),
  so the browser never needs the internal assets hostname.
- Metadata, canonicals, sitemaps, redirects and 404s are part of each route's
  contract, not an afterthought.
- German customer sites; English source routes are canonical, without German
  route wrapper files. Only Swiss German is currently configured.

## Generated code

- **Message catalog** - `packages/i18n/messages/de-CH.json` is the source.
  `pnpm generate` (from `web/`) is the only writer of the git-ignored Paraglide
  output. `pnpm typecheck` runs it first.
- **Route trees** - `src/routeTree.gen.ts` is committed and regenerated by the
  TanStack Router Vite plugin during `pnpm dev` and `pnpm build`. Commit it after
  changing routes; `pnpm typecheck` fails when it is stale.

## Invariants

1. Layering is one-way: `routes → components → data (server functions) →
   *-data packages`. A component never imports a route.
2. Drizzle stays inside data packages. Flyway owns schema and constraints.
3. One validation schema per public form, shared by client and server; errors are
   values at the boundary.
4. Stock and donation capacity use transactions with row locks; the queue insert
   runs in the caller's transaction.
5. Site-specific wording, layout and branding stay in the site. Shared code
   moves to `packages/` only after a second real consumer.
6. Accessibility, responsive behavior, metadata and error states are part of the
   feature.

## Verification

From `web/`: `pnpm check`, `pnpm typecheck`, `pnpm test`, `pnpm build`, and
`pnpm --filter studio build` after any `web/packages/*` change. The full gate is
in [verification](../../development/verification.md); CI parity is in
[CI/CD](../../development/ci-cd.md).

## Known gaps

- Proxy-level rate limiting is not implemented; forms rely on application
  honeypots. See [TD-01](../../work/tech-debt.md#td-01).
- Static asset caching still uses Caddy's one-hour default. See
  [TD-03](../../work/tech-debt.md#td-03).
- Some hard-coded labels and content remain to be translated, and German URL
  translation is unverified. See [open work](../../work/open-work.md).
- Staging environments and end-to-end suites are deliberately deferred.
